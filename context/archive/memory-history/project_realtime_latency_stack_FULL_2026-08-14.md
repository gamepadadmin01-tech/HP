## 🔑 MEASURED latency breakdown (2026-07-20) — the WebView IS the bottleneck
Instrumented on-device (`adb logcat -s GPM:I`, harness shipped in the injected bridge JS, toggle `window.GPM.on`):

| segment | avg | p50 | p95 | max |
|---|---|---|---|---|
| **touch → JS dispatch** | **~6.8 ms** | ~5.7 | **~15** | **25.8** |
| JS → native bridge | 0.71 ms | 0.50 | ~1.8 | 11.2 |
| network RTT USB-tether | **2.5 ms (ROUND trip)** | — | — | — |

One-way ≈ 6.8 (touch→JS) + 0.7 (bridge) + 1.25 (wire) ≈ **8.75 ms — the WebView/JS hop is 78% of it and ~2.7× the whole network RTT.** Measured RTTs: USB tether 2.5 ms, USB debugging 5-6 ms, wireless 10 ms. **This is why PC-side/CPU tuning shows "no change in RTT"** — it optimises the small end. The bridge also fires ~190×/sec × 0.71 ms ≈ 13% of a core **on the JS main thread**, i.e. the send path inflates its own dispatch number. p95 15 ms / max 25.8 ms = jitter, worse for feel than the average.
**→ Priority: native-input-path (Phase 3) BEFORE the Rust server rewrite (~15× the payoff).** Full plan + gotchas: `D:\AKHIL\HP\projects\gamepados\docs\handoffs\SESSION_HANDOFF_2026-07-20.md`.

### 🔑 SERVER-SIDE OPTIMISATION IS A DEAD END — MEASURED 2026-07-21
Two wrong hypotheses were tested and discarded before the real cause was found, so **don't repeat them**: (a) EMA contamination — no, the phone's RTT EMA updates on every ACK and converges in ~1 s; (b) missing Windows tuning — `src/winperf.rs` adds `timeBeginPeriod(1)` + HIGH priority + 1 MB SO_RCVBUF/SNDBUF + DSCP-EF (all report true, dependency-free via direct `extern "system"` to winmm/kernel32/ws2_32) and it made **NO measurable difference**.
**REAL CAUSE (server.py ~line 1520): Python DRAINS THE SOCKET TO THE NEWEST packet per source (`latest[ip] = (data, addr)`) and ACKs only that one.** The Rust server was ACKing EVERY queued datagram, and **the phone recomputes its RTT EMA on every ACK received**, so stale queued frames reported their queue time and dragged the average up. Implementing drain-to-newest (`upsert()` in main.rs) moved Rust's median 3.5 ms → **2.57 ms, floor 1.95 ms (better than Python's best 2.32)**. Valid A/B (same conditions, controller screen): Python 2.32-2.63 tight; Rust pre-fix 2.75-4.53; Rust post-fix 1.95-2.82 with 2 tail spikes.
**HEADROOM VERDICT — the server contributes ~2% of the round trip.** Self-instrumentation (recv→ACK-handed-to-kernel, printed every 5 s) measures **avg ~52 µs, p50 ~47 µs, p95 ~106 µs of a ~2400 µs RTT**, and `batches drained: avg=1.00 max=1` proves it never falls behind at normal load. An infinitely fast server would only take 2.40 → ~2.35 ms. **So further micro-optimising the PC server is NOT worth doing** regardless of Rust's low-level control — the other 98% is the Windows USB/RNDIS + IP stack, the wire, and the phone's send path. Real remaining wins: **AOA direct-USB** (bypasses the IP stack, ~1-2 ms potential) and phone-side work (where Phase 3 already got 3.7×). Same Phase 0 lesson: measure first.

## The 20-byte wire format (immutable shared contract — phone & server must match byte-for-byte)
`<Q H B B B B B B I` LE = ts(u64) buttons(u16) LT(u8) RT(u8) LSx LSy RSx RSy (u8, center 128) authToken(u32 = 0xABCD1234, or QR key on Wi-Fi, or 0 for USB tether). Defined: App.tsx `sendGamepadTelemetry`, gamepad-engine.cpp `GamepadPayload` struct, server.py `PAYLOAD_FORMAT`. Change one side → must change all three.
