## COUNTER SEMANTICS — "+N today" is NOT "+N new" (diagnosed 2026-07-16)
User reported the install totals looked frozen while "+4 today" kept showing. NOT a bug in the writes — verified against the live Supabase DB (206 rows, 24 days): rows are written daily. The labels mislead:
- `unique` (headline) = distinct ipHash **ever** (kind='install') → only moves for a never-before-seen IP.
- `today` (the "+N") = distinct ipHash **that downloaded today**, INCLUDING people already counted. So repeat downloaders keep "+N today" flashing while `unique` legitimately sits still.
- Real data: PC had **0 genuinely new IPs from 2026-07-10 → 07-16** (32 flat) while showing +2/+3/+4 daily; top PC IP downloaded on 7 separate days. App's "+1 today" on 07-16 WAS new (28→29). Identity is IP-based: one household/office = 1; a phone hopping networks = several.
Two real secondary bugs, **both still UNFIXED**: (1) admin.html's 20s fallback poll calls only `loadTickets` — download counters refresh via SSE `download:update` only, so if the stream drops they truly freeze until reload; (2) `todayUTC()` is UTC while the operator is IST → "today" resets 05:30 IST.

It is NOT: **AGP 8.13 (latest stable 8.x line) supports up to API 36.1** — confirmed via official AGP 8.13 release notes. Needed: AGP 8.6.1 → 8.13.x (same major line, i.e. `id("com.android.application") version "8.13.x"` in root build.gradle.kts), `compileSdk`/`targetSdk` 35→36 in app/build.gradle.kts. Gradle (tools/gradle-8.14.4) and JDK 17 already exceed AGP 8.13's own minimums (Gradle 8.13, JDK 17) — **no Gradle/JDK bump needed**. AGP 9.x stays deferred/irrelevant for this deadline.

Must install both via SDK Manager before the bump compiles at all.
3. **Large-screen manifest properties — REAL GAP, not just naming.** Currently shipped (`PROPERTY_COMPAT_ALLOW_ORIENTATION_OVERRIDE` + `PROPERTY_COMPAT_ALLOW_RESIZEABLE_ACTIVITY_OVERRIDES`, both `value="false"`, app-level in AndroidManifest.xml) are a pre-36 compat mechanism. The property that actually gates API 36's "ignore orientation/resizability restrictions on ≥600dp screens" is a DIFFERENT one — confirmed via official docs + AGP source: **`android.window.PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY`, `value="true"`**, same app-level placement. Must be ADDED alongside the existing two when targetSdk becomes 36 — the old ones alone won't cover it. ⚠️ Explicitly temporary: Google states this opt-out "won't work for API level 37+" — the deferred LARGE_SCREEN_TASK_FOR_ANTIGRAVITY.md "Phase 2: real adaptive UI" work becomes mandatory eventually, not yet.
4. **Predictive back — already correct, low risk.** MainActivity.kt already uses the modern `onBackPressedDispatcher.addCallback(this, OnBackPressedCallback...)` (line ~322), NOT the deprecated `onBackPressed()` override, and doesn't dispatch on raw `KEYCODE_BACK`. No `enableOnBackInvokedCallback` declared (fine, predictive back is enabled-by-default for API 36 targets regardless). Should still be device-tested once built — the predictive-back preview/animation over a full-screen WebView hasn't been visually verified.
5. **Confirmed NOT APPLICABLE (grepped against actual code, not assumed):** `windowOptOutEdgeToEdgeEnforcement` (not present — edge-to-edge already migrated in 1.3.16), `scheduleAtFixedRate` (unused), `BODY_SENSORS`/health permissions (app uses `HIGH_SAMPLING_RATE_SENSORS` for gyro, not health sensors), Bluetooth bond APIs (app is WiFi/UDP-only, no BLUETOOTH permission), `MediaStore.getVersion` (unused), photo-picker APIs (unused — CAMERA permission is CameraX/ZXing for QR scanning, not gallery picker).
6. **🚨 STANDOUT FINDING — not required for API 36 today, but a real future risk to the core product:** Android's new **Local Network Permission** gate (opt-in testing phase 25Q2–26Q2, will eventually be enforced) restricts raw TCP/UDP unicast/multicast/broadcast to local-network IP ranges (10.x/172.16.x/192.168.x/link-local) without `NEARBY_WIFI_DEVICES` + a runtime grant. **GamepadOS's entire transport is UDP to the PC over the local network** (per [[realtime-latency-stack]]) — this is exactly the traffic pattern being gated. Not blocking today's targetSdk 36 submission, but when Google flips this from opt-in to default-enforced, pairing/input could silently break for every user without a code update (add `NEARBY_WIFI_DEVICES` + a runtime-permission flow + test under `adb shell am compat enable RESTRICT_LOCAL_NETWORK`). Put this on the roadmap now, ideally landed *before* enforcement, not reactively after users report broken pairing.

Net recommendation: land the AGP 8.13 + targetSdk 36 + new large-screen property bump as the next release after the current closed-test window closes (~2026-07-24), device-test predictive-back + pairing normally, and open a separate follow-up for the Local Network Permission work before Google enforces it.
