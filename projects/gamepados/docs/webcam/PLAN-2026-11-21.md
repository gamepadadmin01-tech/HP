# Phone-as-webcam app — plan (2026-11-21)

Status: **plan agreed (section 7), prototype built.** The PC side is proven on this PC. The phone side is built
and still needs its first test on a real phone. See section 8.

The idea in one line: the phone's camera shows up on the PC as a normal webcam, so Zoom, Meet in Chrome,
Teams, Discord, OBS and the Windows Camera app can all pick it. It works over home Wi-Fi or a USB cable,
with no cloud servers, the same way GamepadOS does.

---

## 1. What I read first, and what we can reuse

**How GamepadOS pairs today** (read in `pc-server-rs/src/pairing.rs`, `qr.rs`, `netdetect.rs`, and the
phone's `MainActivity.kt` + `Dialogs.tsx` / `App.tsx`):

- The PC keeps a **pairing key**: 8 random letters/digits, saved in
  `%LOCALAPPDATA%\GamepadServer\pairing_key.txt`. It stays the same across restarts.
- The server window shows a **QR code** that holds three things: `PC address, port, key`
  (for example `192.168.1.34,7777,777a51b3`).
- **Wi-Fi:** the phone scans that QR once, remembers the PC, and reconnects by itself next time.
  Every packet carries the key, so a stranger on the same Wi-Fi cannot drive the PC.
- **USB cable:** the phone turns on USB tethering, and the app sends a "hello" to everyone on that cable
  (a *broadcast*: one message addressed to the whole little network). Only the phone and the PC are on a
  cable, so no key is needed there. The server already knows how to tell a cable from Wi-Fi.
- To be honest: on Wi-Fi there is **no automatic finding of the PC** today. The first connection is always
  a QR scan; after that the phone remembers it. The webcam app works the same way.

**Reused as-is or nearly:** the QR scanner (CameraX + ZXing), the remembered-PC list, the USB-tether
watcher, the Wi-Fi low-latency lock, the calm React UI (`CalmShell`, `CalmConnect`, `CalmSettings`,
`PlanPanel`, `AccountAuth`, `motion.ts`), the sign-in and Lifetime purchase, the server window's look,
the installer (it already runs as admin and already allows the server through the firewall on any TCP
port — so no new firewall rule is needed).

## 2. Screens

**Phone app** (same warm flat look as GamepadOS, same fonts, same pop-up motion):

1. **Connect** — copy of GamepadOS's Connect screen: "Scan the QR on your PC", the remembered PCs,
   and "Plug in USB" which connects by itself.
2. **Live** — the camera picture fills the screen. One bottom bar: switch front/back, flashlight,
   mirror, quality chip (for example `720p · 30`), **Stop**. A small badge: `Live on DESKTOP-ABC`.
   A "dim screen" button: the picture keeps going to the PC while the phone screen goes almost black
   (saves battery and heat).
3. **Settings** — picture quality, frames per second, which camera opens first, keep-awake, language.
4. **Account / Plan** — the same sign-in and Lifetime panel as GamepadOS.

**PC side** (the existing Gamepad Server window, not a new program): one new card,
**"Phone camera"** — `Off` / `Live · 720p 30 · Redmi Note 12`, and the name Windows shows to apps
(working name `GamepadOS Camera`). The same QR pairs both phone apps.

## 3. How the picture travels (the video pipeline)

```
Phone camera
  → the phone's video chip squeezes each frame into H.264
  → one steady connection over Wi-Fi/USB (new port 7780)
  → Gamepad Server un-squeezes it with Windows' own H.264 decoder
  → hands the frames to the "virtual camera" helper
  → Zoom / Meet / Teams / Camera app see a normal webcam
```

New words, one at a time:

- **H.264** — the standard way to squeeze video. A raw 720p picture is ~1.4 MB; squeezed it is a few KB.
  Every phone has a chip that does this for free (Android calls it **MediaCodec**), and every Windows PC
  has the matching un-squeezer built in. So it costs almost no battery and no money.
- **TCP connection** — GamepadOS sends gamepad input as separate small "postcards" (UDP), where losing
  one does not matter. Video is different: if one piece is lost the picture smears until the next full
  frame. So video uses a **TCP** connection, which is more like a phone call: everything arrives, in
  order. On home Wi-Fi this adds very little delay. The first message proves the pairing key, so a
  stranger cannot push video into your PC.
- **Virtual camera** — Windows 11 has a built-in way to add a pretend webcam without installing a driver
  (`MFCreateVirtualCamera`). The catch: Windows does not take frames from our program directly. A Windows
  background service asks a **small helper file** that we ship (`GamepadCam.dll`) for each frame. So the
  server puts each frame into a shared piece of memory, and the helper file reads it from there.
  The installer registers the helper file once (it already runs as admin).

Target: 720p at 30 fps, about 0.1–0.2 s of delay, about 4 Mbit/s on Wi-Fi.

## 4. Where the code goes

- `apps/webcam-android/` — the new Android app (Kotlin shell + WebView, copied pattern from
  `android-client`, its own package name, so it is a separate Play Store listing).
- `apps/controller-ui/` — a third UI bundle built from the same styles and components
  (`npm run build:webcam`), so the theme is literally shared, not copied.
- `apps/pc-server-rs/src/camera/` — receive, decode, hand to the helper. `apps/pc-server-rs/vcam/` —
  the helper DLL. Same Rust toolchain that is already on this PC.
- Backend: the existing account + entitlement code; the webcam app asks the same "is this account
  Lifetime?" question.

## 6. Risky parts — said plainly

1. **The helper file runs inside a Windows service**, under a locked-down account, not inside our
   program. Permissions for the shared memory, and debugging, are fiddly. Microsoft publishes a working
   sample of exactly this, so it is known to be possible — it is just the hardest piece, so I build it
   first.
2. **Microphone is not free.** Windows 11's built-in virtual camera covers **video only**. A pretend
   microphone needs a real audio driver, which must be signed by Microsoft — weeks of work and a cost.
   Most people already have a headset or laptop mic, so I suggest video-only first (question 3).
3. **Windows 10 does not have the built-in virtual camera.** Version 1 says clearly "Windows 11 needed".
4. **Some apps read the camera list only when they start** — the user may need to reopen Zoom after the
   phone connects. The camera can stay listed (showing a "connect your phone" picture) while the server
   runs, which avoids most of this.
5. **Android camera rules:** to keep streaming with the screen dimmed or another app open, Android needs
   a "camera foreground service" (a permanent notification) and Google Play asks us to declare why.
   This is normal for webcam apps but must be filled in correctly on the listing.
6. **One purchase for two apps on Google Play:** Play allows an app to unlock things bought elsewhere on
   the same account, but the webcam app must still sell its own Lifetime through Play Billing, and must
   not point users to cheaper prices outside Play. I check the current wording of the Payments policy
   before release — not a blocker for the prototype.
7. **Heat and battery** on long calls. Hardware H.264 + dim screen keeps it reasonable; 1080p60 will run
   warm on cheap phones.

## 8. Prototype status (2026-11-21, end of day 1)

### Proven on this PC (Windows 11, build 26300)

- **"CamOS Camera (Windows Virtual Camera)"** appears in Windows' camera list, next to the laptop camera
  (and DroidCam, which is also installed here).
- An app opening it through Windows' camera service gets **1280×720 at a steady 30 fps**.
- Full chain tested with a pretend phone: real H.264 video → CamOS protocol on TCP 7780 → pairing-key check
  → Windows' H.264 decoder → named pipe → camera DLL inside Windows' camera service → app. A frame read back
  out of "CamOS Camera" showed the test picture with correct colours and shape.
- A wrong pairing key is refused; a second phone gets "busy".
- With no phone streaming, apps see a calm warm-brown "waiting" picture instead of a frozen one.
- All 160 existing Gamepad Server tests still pass. Two start-up risks were found and fixed before
  committing: (1) a Windows-11-only function is now looked up at run time, so the server still starts on
  Windows 10; (2) Windows' media library is delay-loaded and checked, so it still starts on "Windows N".

### Built, not yet tried on a phone

- `test-builds/camos/CamOS-0.1.0-prototype-DO-NOT-UPLOAD.apk` (debug-signed, not for any store).

### How to test it end to end (about 5 minutes)

1. Close the installed Gamepad Server (tray → Exit). The test build uses the same port and the same pairing key.
2. Run the test server: `apps\pc-server-rs\target\release\pc-server-rs.exe` (no flags: the window opens by default; `--gui` is not a flag).
   The console should show `camera : "CamOS Camera" ready`.
3. Install the APK on the phone (`adb install -r …\CamOS-0.1.0-prototype-DO-NOT-UPLOAD.apk`), open CamOS,
   allow the camera, tap **Scan PC QR code**, scan the code in the server window.
4. On the PC open the **Camera** app (switch camera until "CamOS Camera"), then **meet.google.com** in Chrome →
   Settings → Video → "CamOS Camera". The server window's bottom line should say `Phone camera live · …`.

### One-time setup that the installer must do later

The camera DLL is registered once, as admin:
`regsvr32 "D:\AKHIL\HP\projects\gamepados\test-builds\camos\camos_vcam.dll"` (done on this PC on 2026-11-21).
To remove it: `regsvr32 /u` on the same path. For release, `installer/GamepadServer.iss` must copy
`camos_vcam.dll` next to `GamepadServer.exe` and register it (`regserver` flag). That is not done yet.

## 9. Round 2 — owner's first phone test (2026-11-21, evening)

**What he found:** (1) the app was locked sideways; (2) after scanning the QR the app said "paired", but Start camera
said the PC was not responding; (3) he wanted two sections only, every camera setting, the ad-for-HD offer on the home
page, and Premium in Settings (Premium = special filters + no watermark + HD).

**Why Start failed:** the Gamepad Server running on his PC was the installed 2.1.5 (14 Nov), built before CamOS. It has
no camera part, so nothing listened on port 7780. "Paired" was misleading: scanning only saved the address on the phone.

**What changed**
- Pairing now really checks the PC: the phone does the full key handshake with a "check only" flag (proto flags bit 0),
  so the home screen says *PC ready*, *Update Gamepad Server* (PC answered but has no camera part), *Can't reach your
  PC*, *Pairing key changed* or *PC busy*. It re-checks every time the home screen opens.
- Rotation (owner's rule): the app turns with the phone before Start. On Start the screen holds still in the chosen
  picture shape (Settings → Picture shape: Auto / Wide / Tall). A tall picture reaches Windows apps fitted with black
  bars, not squashed (DLL `scale_nv12` keeps the shape).
- New picture engine on the phone (`GlPipeline.kt`, OpenGL): turns the camera upright for any way the phone is held,
  crops to the shape, applies the Premium filters, and draws the CamOS mark for free users — on both the PC picture and
  the phone preview, so the preview is exactly what the PC gets.
- Settings (all in one tab): quality 480/720/1080 (1080 needs Premium or an ad unlock), frame rate 15/24/30/60 (only
  what the lens supports), automatic or manual bitrate (1–20 Mbit/s), picture shape, lens (every lens the phone reports),
  zoom (below 1× = ultra-wide where available), focus auto/manual + distance, stabilisation, flashlight, mirror preview,
  brightness, white balance, anti-flicker 50/60 Hz, noise reduction, auto-dim. Filters (Premium): colour looks (warm,
  cool, vivid, B&W, film), face smoothing, low-light boost. Background blur is shown as "next update".
- Settings is a short list of categories (Premium, Video quality, Lens & focus, Light & colour, Filters, Phone
  screen, Your PC, About), each showing its current values; tapping one slides its own page in, Back returns (owner:
  "divide the settings based on the category and type").
- Home: "Unlock HD for 45 minutes" card with a live countdown; when the 45 minutes end mid-stream the stream restarts
  in 720p by itself. Premium card at the top of Settings.
- Live screen: switch camera, flashlight, an Adjust panel (zoom, brightness, colour look, face smoothing), dim, Stop.
  Every change applies while streaming.
- Windows camera now also offers 1280×720 and 1920×1080 at 60 fps.
- Test builds only: "pretend Premium" switch and a 5-second pretend ad, so every screen can be tried before billing
  and ads exist. Ad-unlocked HD keeps the watermark (Premium removes it) — owner's wording: Premium = no watermark.

**Still to do:** real ads + Play billing; background blur (needs an on-phone AI model); USB; camera foreground service;
installer ships and registers `camos_vcam.dll`; **a Gamepad Server release with the camera part** — until then every
user's installed server is "too old" for CamOS.

### Full re-check (2026-11-21, night) — what it found and fixed
- **Picture would have been sideways on a real phone.** Android already turns camera frames upright for the phone's
  natural orientation (and mirrors the front camera) in the SurfaceTexture matrix; the engine turned them again.
  Now it reads the turn and the mirror from that matrix, undoes the mirror (PC gets the true picture) and turns only
  by the screen rotation. Checked against Android's own matrix maths for back/front cameras and both sensor mountings,
  and the shaders were compiled and run in WebGL (same shader language): all compile, rotations land correctly.
- Start right after the "is my PC ready?" check could say "another phone is streaming" (the PC was still closing the
  check): one quiet retry.
- Streaming died silently if the app went to the background for a moment: the camera now reopens on return.
- Wi-Fi drops mid-stream show a plain message instead of "Broken pipe".
- "Update Gamepad Server" detection: the installed 2.1.5 opens TCP 7777 to this PC only, and Windows' firewall drops
  knocks on closed ports, so from the phone an old server and a PC on another Wi-Fi look the same. The home screen
  now says "PC not answering" with both causes and a "Get the PC server" button; "Update Gamepad Server" only when the
  PC actively refuses.
- PC side re-run: camera tests pass; check = ready / key changed / busy-while-streaming all correct; pretend phone →
  "CamOS Camera" at 30 fps with the right picture, on the PC's new address 10.0.5.28.
- One old network test (`pktinfo` reply pinning) fails while a VPN adapter (ProTUN) is on — not CamOS code.
